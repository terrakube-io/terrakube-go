# Vendored Terrakube OpenAPI documents

`v{VERSION}.json` is the OpenAPI document of Terrakube API `{VERSION}`. The library targets one version at a time: the file matching the `APIVersion` constant in `client.go`. CI checks the client against it (`speccheck check --fail-on-missing`).

| File | Source | Fetched |
|------|--------|---------|
| `v2.34.1.json` | `GET /doc` of a Terrakube 2.34.1 API server (docker-compose stack) | 2026-11-13 |

## Format

Files are normalized by `speccheck fetch`: parsed as OpenAPI 3, re-encoded as indented JSON with sorted keys, and `info.version` set to the version (Elide leaves it empty). Do not edit them by hand; fetch again instead.

## Where documents come from

- **A running server** (current versions). Terrakube's API is generated by Elide and serves its document at `/doc` to authenticated users:

  ```bash
  TERRAKUBE_TOKEN=... mise run spec-fetch -- --server=https://terrakube-api.example.com --version=2.35.0
  ```

  The document does not state its version, so `--version` is required. The token is read only from `$TERRAKUBE_TOKEN` and never printed.

- **GitHub** (older versions). `terrakube-io/terrakube` publishes `openapi-spec/v{X_Y_Z}.yml`, last updated for 2.27.0. The YAML on the default branch is malformed since its conversion from JSON; the commit before that conversion has a valid file:

  ```bash
  mise run spec-fetch -- --version=2.27.0 --ref=0d12793cf3791f7bc55408a9d9a7bde983cfb8f7
  ```

  Set `$GITHUB_TOKEN` to avoid the unauthenticated rate limit.

## Notes on the Elide document

- Every relationship's `data` is rendered as an array; cardinality comes from the `/relationships/{name}` endpoints.
- Only some nested paths are listed, but the server serves every relationship chain. `speccheck` resolves undocumented paths hop by hop through the relationships.
- Some fields the server returns may be hidden from the document. Fields the document does not list are kept in the client and marked `// DEPRECATED (...)` for review, never deleted.
